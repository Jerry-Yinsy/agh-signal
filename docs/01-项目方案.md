| 项 | 内容 |

| 项目名称 | agh-signal：基于 AGH 的信号配时自动寻优与验证闭环 |

| 具体方向 | B4 科研 Agent 与 Harness 工程（可加选 D4 环境能源与城市系统） |
| 一句话创意 | 用 Agnes Harness 编排"仿真调用—参数寻优—边界工况验证—异常重试"的多智能体闭环，把路口信号配时的寻优与验证从人工数小时压缩到秒级，并自动产出可复现的验证报告。 |

## 二、问题与价值

城市路口的信号配时通常依赖工程师手工试算：改一版配时，再打开仿真或翻历史流量手工比对延误，一轮几十分钟，而且往往只验证一两个"正常工况"。真实道路上更常见的是高峰、潮汐偏斜、事故降容这类边界工况，恰恰在这些工况下配时方案会失效。

本项目把这件事做成闭环：

1. 把"评估一套配时好不好"变成机器可调用的工具（确定性分析模型 + SUMO 微观仿真）；
2. 让 AGH 上的智能体驱动寻优、验证、复盘，人只审结论；
3. 每条结论都带证据：评估了多少方案、与两个基线的对比、边界工况是否仍可行、不可行时的处置建议。

价值落点：江苏省内通勤走廊的潮汐路口（早高峰进城、晚高峰出城）与校园周边路口，都是"低饱和度但方向不均衡"的典型场景，短周期加动态分配的收益明显，而且不需要改造硬件。

## 三、目标与验收指标（KPI）

| 指标 | 目标 | 验证方式 |
| --- | --- | --- |
| 寻优耗时 | 单工况 < 1 秒（人工试算约 30–60 分钟） | CLI 实测 + 报告中的方案评估数 |
| 车均延误下降 | 相对现状固定配时 ≥ 15% | artifacts/report-normal.md 基线对比表 |
| 约束满足 | 所有输出方案满足最小绿灯与最大饱和度约束 | 违例列表为空 |
| 边界鲁棒 | 4 个边界工况全部给出结论 | artifacts/verification.md 边界明细表 |
| 失败可见 | 过饱和工况必须被显式拒绝 | 失败样例检查项 |
| 可复现 | 同 seed 两次运行结果一致 | 复现性检查（哈希） |

## 四、系统架构

AGH 会话负责规划与编排，工具层只认稳定契约：AGH 工具插件调用 `src/cli.mjs`，CLI 输出 JSON。

```
AGH 会话（规划 → 调用工具 → 汇总 → 出报告 → 异常重试）
   └─ plugin/index.mjs 注册 5 个工具：traffic_scenarios / traffic_simulate /
      traffic_optimize / traffic_verify / traffic_report
        └─ src/cli.mjs（工具契约层，stdout 只输出 JSON）
             ├─ model.mjs     确定性分析模型（快速筛选）
             ├─ optimize.mjs  网格全局寻优 + Pareto + 基线对比
             ├─ verify.mjs    5 项自动验证
             └─ sumo.mjs      SUMO 微观仿真（独立复核）
```

设计要点：

- 工具契约稳定：替换模型或仿真器不影响上层编排。
- 双层评估：宏观模型负责毫秒级寻优，SUMO 负责对最终方案做独立复核，两者对照即"验证严谨性"。
- 失败显式化：不可行方案一律带 `violations` 返回，绝不输出看似能跑的坏方案。

## 五、模型与算法

### 5.1 分析模型（src/model.mjs）

- 相位方案：两相位（南北 / 东西），允许式左转；损失时间每相位默认 4s。
- 饱和流率：直行 1800 veh/h、左转 1200 veh/h（经验值），重车比例按 1 − 0.15 × 重车率 折减。
  口径说明：模型把每个"进口 × 转向"当作**一个车道组**处理，饱和流率取车道组值，因此不体现车道数几何。
- 关键流率比：相位内各流向 v/s 的最大值，Y = y_NS + y_EW。
- 延误：Webster 均匀延误 d₁ = 0.5C(1−λ)²/(1−min(1,x)λ)；未饱和时随机延误 d₂ = x²/(2q(1−x))，
  x ≥ 1 时改用溢出延误 d₂ = (x−1)C + 60（60s 为再排队常数的经验上限，属有意简化）。
- 通行能力 c = s·λ；饱和度 x = v/c。
- 排队（单位：辆）：平均排队按 Little 定律由**均匀延误**给出，avgQueueVehicles = Σ qᵢ·d₁ᵢ（各流向之和）；
  最大排队取最不利流向的 q·(C−g)，即一辆车若恰好红灯到达所需等待的排队长。
  ⚠️ 不要用总延误（含随机/溢出延误）去算排队，也不要误用 Σ qᵢ·dᵢ —— 那是延误车辆秒，量纲是 veh·s/h。
- 停车率近似 Σ v(1−λ)/Σ v；人员延误按平均载客系数换算（默认 1.3 人/车）。

### 5.2 寻优（src/optimize.mjs）

- 设计变量：周期 C ∈ [60,160]s（步长 2s）与南北绿灯 g_NS，东西绿灯 g_EW = C − 损失时间 − g_NS。
- 约束：g ≥ 8s；所有流向 x ≤ 0.95；Y < 1。
- 模型确定性且单次评估小于 0.1ms，因此直接网格穷举即为全局最优，单工况评估约 200–900 个可行方案，也避免了"调参调不出更好结果"的风险。
- 双目标：车均延误（效率）与最差进口延误（公平性），输出 Pareto 前沿与公平性优先方案。
- 对照基线：现状固定配时（90s 均分）与 Webster 经典配时公式。

### 5.3 与现实校准

模型不追求替代专业交通仿真软件，只承担快速筛选；最终方案由 SUMO 复核。这条分工必须写进作品说明，避免过度承诺。

## 六、验证设计

`node src/cli.mjs verify` 跑 5 项检查并写入 artifacts/verification.md：

| 检查 | 内容 | 通过判据 |
| --- | --- | --- |
| 自洽性 | 总延误与车均延误能否由流向明细重算 | 误差 < 0.01s |
| 交叉验证 | 网格最优 vs Webster 公式 | 周期差 ≤ 20s、延误差 ≤ 25%（**口径一致性核对**，两条路径共用同一套延误公式，不构成独立验证） |
| 复现性 | 同 seed 两次生成的 SUMO 车流与需求剖面哈希一致、换 seed 必须改变 | 哈希一致且改变 |
| 边界工况 | 基准配时在 4 个扰动工况下的可行性与收益 | 每个工况都有明确结论 |
| 失败样例 | 过饱和必须被拒绝 | 可行方案数为 0 且给出原因 |

补充：`node tools/regression-test.mjs` 是 16 项不依赖 SUMO 安装的回归测试，锁住历史缺陷
（SUMO 需求放大 8 倍、重车比例失效、相位映射周期不守恒、排队量纲错误、复现性检查形同虚设等）。

三类测试样例（官方必填项）：

| 类型 | 工况 id | 预期结果 |
| --- | --- | --- |
| 正常 | normal | 输出候选方案，车均延误较现状下降 ≥15% |
| 边界 | peak / skew / heavy / incident | 给出基准配时是否仍可用的判断与重新寻优收益 |
| 失败 | oversaturated | 判定不可行，输出降级建议，不产生配时方案 |

## 八、风险与降级

| 风险 | 影响 | 降级方案 |
| --- | --- | --- |
| 拿不到真实路口流量 | 工况可信度下降 | 用公开流量数据加现场视频计数，并在说明中标注来源 |
